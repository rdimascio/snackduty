# Snackday engineering guide

Snackday is a Bun monorepo for a Lesto web application and a native SwiftUI iOS application.

## Commands

- Install dependencies with `bun install`.
- Run all checks with `bun run gate`.
- Format with `bun run format`; lint with `bun run lint`.
- Run a workspace script with `bun run --filter <workspace> <script>`.
- Boot a seeded local scenario with `bun run dev:scenario`; it prints the `/dev/sign-in` link and is ready in about a second. `bun run check:scenario` seeds, verifies every role over HTTP, and tears it down.
- Run the browser end-to-end suite with `bun run e2e` (or `bun run e2e e2e/duties.test.ts` for one file). It needs Chromium for `playwright-core`; install it once with `bunx playwright-core install chromium`. It also needs Bun 1.4.2 or later: Bun 1.3.5 drops Playwright's browser connection mid-run, so `scripts/e2e.ts` refuses it. On Bun 1.3.5, run `bunx bun@1.4.2 scripts/e2e.ts`. The CI e2e job pins Bun 1.4.2; every other job keeps the repo's 1.3.5.

## End-to-end suite

- `e2e/` drives the real app in headless Chromium as every seeded role. One file per area: `navigation`, `team`, `roster`, `schedule`, `duties`, `ballplayer`, `lesson-answers`, `csp`, plus `harness` for the suite's own guards. One `describe` per role. The second-team guardian has two: one for the Falcons (refused) and one on their own Comets team, where every management write is refused and the Comets owner (`default`) makes the same call as the control.
- `scripts/e2e.ts` builds the client bundle, then runs `bun test ./e2e/`. Each `describe` calls `useScenario()` (`e2e/support/scenario.ts`): it seeds a fresh SQLite file with the SQL seed, switches it to WAL so the test's reads never make a server write fail with `SQLITE_BUSY`, boots `e2e/support/offline-scenario-server.ts` (which wraps `apps/web/test/support/csp-scenario-server.ts`) on a free port, and launches Chromium. Tests in one `describe` share that server and run in order.
- `asRole(scenario, role, run, brand?)` (`e2e/support/session.ts`) opens a fresh browser context signed in through `POST /api/dev/sign-in`, and fails the test on any CSP violation except Lesto's `data-lesto-layout` wrapper style, any 429, any page error and any console error. An expected 4xx must be declared with `session.open(path, status)`, `refused(...)` or `session.allowFailedResponse(...)`. After `run`, `session.settle()` waits for the page `load` event and a round trip through the violation binding, so every report the page queued has arrived before `problems()` is read; call it yourself before reading `problems()` on a session from `openSession`.
- The 429 check is a placeholder for the signed-in app: its default rate limit is not reached by any e2e test. The coach `POST /book` limit answers 429 and is covered in `apps/web/test/coach-booking.test.ts`.
- Every action test asserts the server state after the click: it reads the SQLite file (`scenario.query`) and reloads the page. Every negative test calls the API from the page with that role's cookie through `refused(...)` and names the guard it proves.
- A seeded email is a label, not a verified identity. `e2e/team.test.ts` covers an email-bound invitation by inserting a `verified_identity_emails` row for the `default` adult in its own scenario; the stranger's seeded invitation is bound to the person, so it needs none.
- Known app bugs stay as `test.failing` tests named `known bug: …`. When a fix lands, the test starts to pass, `bun test` reports it, and the `failing` marker must go. None are open today.
- A team page a role may not open (`/app/roster`, `/app/duties`, `/app/roster/:participantId`) must answer 404 with the shared not-found text from `routes/not-found.tsx`, no skeleton, no `data-stck` and no app inline script; `expectRenderedNotFound` (`e2e/support/pages.ts`) checks all four and ignores `type="application/json"` island blocks and the Lesto dev overlay scripts.
- Wait on a real condition (a response, a `load` event, a URL change, visible text), never a sleep. A same-URL `location.assign` does not change the URL, so wait for that navigation's response and the new page's `load` event.
- The suite never uses the network. The scenario server answers the Reel catalog and episode URLs from the fixture in `e2e/support/reel-fixture.ts`, and every browser context answers that fixture's poster URL on `REEL_MEDIA_ORIGIN` from `e2e/support/fixtures/lesson-poster.png`, so the CSP `img-src` path still runs. Any other non-loopback request, from the server or the browser, is blocked and fails the test that made it through `session.problems()`. Every context blocks service workers, and a `context.on("request")` backstop records every non-loopback URL, redirect hops included, because Playwright's route handler never sees a redirect hop. Chromium also runs behind a proxy on an unused loopback port that bypasses only loopback hosts, so a hop that escapes the route fails to connect instead of reaching the network. The scenario server's loopback `fetch` follows redirects by hand (`redirect: "manual"`) and rejects an outside `Location` (`e2e/support/offline-fetch.ts`). `e2e/harness.test.ts` proves both, and that `startScenario` removes its server and scratch directory when a start-up step fails. Check it with `sandbox-exec` and a profile that denies every outbound connection except `localhost`.
- `e2e/lesson-answers.test.ts` proves the production card write guard: every role that is not the child's guardian posts a correct answer to `POST /api/teams/:teamId/lessons/current/answers` and the child's `lesson_answers` and `skill_events` rows stay the same; the guardian's own answer is the positive control.
- With `E2E_ARTIFACTS_DIR` set (`bun run e2e` sets `.artifacts/e2e`), a failing test saves a Playwright trace, a full-page screenshot and its problems there. CI uploads that folder on failure.

## Dev seed and roles

- `seed/` holds numbered SQL files (`001_people.sql` … `009_calendar_feeds.sql`). `apps/web/app/dev/seed-database.ts` creates a new SQLite file, runs `installSessionSchema` and `applicationMigrations`, then applies every `NNN_name.sql` in name order in one transaction, before `lesto dev` boots. The seed is dev-only and SQLite-only: dates use SQLite `date()`/`strftime()` relative to now, and production (Postgres) never runs it.
- Seeded teams run in `America/Phoenix` (no DST), so `starts_at_utc` is local time plus seven hours. Every event falls on or after today and within the next 21 days, on any weekday the seed runs: a Tue/Thu Falcons practice series, three Saturday games (one cancelled), and one Comets clinic.
- The seed also holds open and claimed duty slots on games and the next three practices, guardian RSVPs, a week of `skill.events/v0` for Avery (a few days for Blake), two pending Falcons invitations, and Pat Parent's Falcons calendar feed. Invitation and feed tokens are fixed synthetic values; the scenario start-up text prints their links.
- `apps/web/app/dev/seed-personas.ts` is the one module for seeded ids: `SEED_PERSONAS`, `SEED_TEAMS`, `SEED_CHILDREN`, `SEED_INVITATIONS`, `SEED_CALENDAR_FEED`, `SEED_SCHEDULE`. Keep the ids stable; end-to-end tests import them. Emails are labels only: the seed writes no `verified_identity_emails`, because a dev identity never proves an email.
- Roles. Sign in at `/dev/sign-in` (one button per role) or `POST /api/dev/sign-in` with `{"persona": "<key>"}`. No body signs in `default`.

Both exist only when `SNACKDAY_DEV_SIGN_IN=true`.
- Add seed data: add rows to the file for that area, or add the next numbered file. Use fixed ids that start with the table prefix plus `_seed_`, relative dates, and `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')` for timestamps. Add any id a test needs to `seed-personas.ts`. Write no SQL comments. Then run `bun run --filter web test test/dev-seed-schema.test.ts test/dev-seed-roles.test.ts`.
- Every seeded team names its organization: `seed/002_teams.sql` writes `teams.organization_id` as the literal `'org_snackday'`, which must equal `SNACKDAY_ORGANIZATION_ID` in `apps/web/app/lib/server/organizations.ts`; `apps/web/test/organizations-migration.test.ts` fails when a seed team row leaves it out or names another value. A new seed team does the same.
- `apps/web/test/dev-seed-schema.test.ts` applies the seed to a freshly migrated database and fails when a column or table changes under it; it also checks that occurrences match `scheduleDates`, that the event span holds with the clock fixed to each of the seven weekdays (`applySeed(db, { now })` replaces SQLite `'now'` with that instant), that skill events parse, and that token hashes match. `apps/web/test/dev-seed-roles.test.ts` signs in every role and checks its team access.

## Conventions

- Use strict TypeScript and ESM. Do not weaken compiler or lint rules to land a change.
- Keep `Person`, `Account`, `Household`, `Participant`, and team membership as separate domain concepts. Children do not require accounts.
- Authorize every server-side operation; client visibility is not an authorization boundary.
- Player cards: a coach (a role holding `roster.manage`) reads, read-only, the card of a child with an active membership in an active season of that team (`mayReadParticipantCard`). Every write (lesson answers, skill events, the seed route) stays guardian-only through `mayManageParticipant`.
- `apps/web/app/dev/` holds development-only routes, the seed runner and the role sign-in. `POST /api/dev/teams/:teamId/participants/:participantId/skill-events`, the role sign-in and `/dev/sign-in` are registered from `apps/web/lesto.app.ts` only when `SNACKDAY_DEV_SIGN_IN=true`; the production runtime and Worker never import `app/dev`, and `apps/web/test/dev-skill-events-flag.test.ts` checks that they answer 404 there. The seed route and the SQL seed are the only paths that may backdate a skill event.
- `patches/@lesto%2Fobservability@0.3.0.patch` stops the browser RUM client from recording a resource span for its own `POST /__lesto/browser-spans`; without it, every sampled tab posts in a loop in every mode. Keep `@lesto/observability` pinned to the patched version, and keep one rate limiter for every request in every mode. `apps/web/test/rum-beacon-loop.test.ts` guards it.
- Roster name keys: `memberships.child_identity_key` and `guardian_relationships.guardian_name_key` hold SHA-256 hex digests behind two partial UNIQUE indexes (`apps/web/app/lib/server/roster-name-keys.ts`): one active child per name + birth date per season, and one active placeholder guardian per name + relationship per child. Every write that inserts a participant membership or a placeholder guardian link, or changes a child's name or birth date or a placeholder guardian's name, must write the key with `storedChildIdentityKey` / `storedGuardianNameKey` in `apps/web/app/lib/server/people-identity.ts`. A CHECK refuses a participant membership without a key; an account-bound guardian link stores NULL, so a placeholder link written without a key is not caught. The JS duplicate checks decide the answer; `withRosterNameKeyBackstop` maps an index conflict (and, for import, a Postgres deadlock) to the same 409 or import verdict. The dev seed runner suspends CHECK constraints while it runs the SQL files and then fills the keys, so seed SQL leaves them out; a raw-SQL test insert of a participant membership must compute the key.
- Queue side effects must be idempotent and persist their state before delivery.
- Never include child-sensitive data in logs, analytics, or notification previews.
- Use `apply_patch` for deliberate source edits and preserve unrelated work in the shared worktree.
- Infrastructure conventions come from the sibling Lesto repository at `../crack`; read its `AGENTS.md`, `ARCHITECTURE.md`, and `CONVENTIONS.md` before changing infrastructure.

## Brands

- One app serves three brands: Snackday, Ballplayer, and the coach site (DiMascio Baseball). Same deploy, data model, and accounts; sessions stay per host.
- Coach brand: `dimasciobaseball.com`, `www.dimasciobaseball.com`, and the dev host `coach.localhost` map to `coach` in `brand.ts`; other subdomains (`learn.`, `media.`) stay Snackday. On the coach host, `GET /` renders `app/coach/home-page.tsx` and `/fonts/*` serves `public/fonts`, and the lesson request and article paths below are served; only the platform allowlist falls through and everything else is a plain 404. It gets `COACH_CONTENT_SECURITY_POLICY` (the same strict policy as Ballplayer) and shares the Ballplayer theme tokens through `data-brand="coach"`. `apps/web/test/coach-brand.test.ts` covers dev and production.
- Coach lesson requests: `GET /book` (`app/coach/book-page.tsx`) is a server-rendered form with no client bundle; it posts as a plain HTML form to `POST /book`, which validates with `lessonRequestSchema` (`app/coach/booking-form.ts`), stores one `lesson_requests` row and one `lesson_request_outbox` row in one batch (migration `019_create_lesson_requests` in `app/coach/lesson-requests.ts`), and answers 303 to `GET /book/sent`. A rejected post re-renders the form with 422 through the coach-only `/__coach/book-retry` page, which the brand router never forwards. A filled `website` honeypot gets the same 303 and stores nothing. `/book`, `/book/sent` and `POST /book` are on the coach allowlist only; they 404 on Snackday and Ballplayer, and on the coach host when `routeBrands` gets no `CoachBooking` (`app/coach/booking-pages.ts`). Shared coach constants and `lessonTypes` (each with a stable `id`) live in `app/coach/content.ts`, a plain `.ts` file, because `scripts/` typechecks `brand-routing.ts` without JSX. The player's name is never asked for; only the age is stored. The age range (`PLAYER_AGE_MIN`, `PLAYER_AGE_MAX`, 5 to 14) lives in `app/coach/content.ts` and feeds the schema, the form input and the home page text.
- The coach email goes through `EmailTransport` to `SNACKDAY_COACH_REQUEST_TO` (validated in `runtime/config.ts`), with `replyTo` set to the parent's validated email, which `runtime/resend-email.ts` sends as Resend's `reply_to`. Invitation and sign-in emails set no `replyTo`. With no address or no transport the request is stored and its outbox row waits unqueued; the next runtime that has both queues it on boot. A job that fails for good (a permanent provider error or 8 attempts) logs `lesson_request.delivery_failed` with only the job id, and every boot with both settings re-queues failed email jobs whose outbox row is still `pending` (`recoverFailed`), so the email is re-sent at the next boot rather than dropped; a recovery error is reported through `onSchedulingError` and never blocks boot; `apps/web/test/coach-lost-leads.test.ts` covers it. Every parent-typed value is quoted with `quotedEmailText`. Spam protection is the honeypot, the kernel's per-client rate limit, and a stricter limit on `POST /book` only (`app/coach/booking-rate-limit.ts`: a token bucket of 5 posts per client IP that refills one post every 2 minutes, in the same SQL rate-limit store under a `coach-booking:` key prefix; over it answers 429 and stores nothing); Turnstile or any third-party script needs a CSP change and Ryan's explicit yes. `apps/web/test/coach-booking.test.ts` covers the flow.
- Coach articles: parent guides are Markdown files in `apps/web/app/coach/articles/<slug>.md` with frontmatter `title`, `description`, `slug` (must match the file name), `published` (`YYYY-MM-DD`), `draft` (boolean) and an optional `episode` (a slug from `https://learn.dimasciobaseball.com/episodes.json`; never invent one). `app/coach/articles.ts` parses them with a strict schema; `app/coach/markdown.ts` reads only level 2 and 3 headings, paragraphs, lists, bold, italics and same-origin links (any other link fails at boot), and `app/coach/article-pages.tsx` renders them on the server with no client bundle. Routes on the coach host only: `GET /articles` (newest first), `GET /articles/<slug>`, `GET /sitemap.xml` (home, `/book` when booking is open, `/articles` and every served article, with absolute `https://dimasciobaseball.com` URLs) and `GET /robots.txt`. An unknown slug is a plain 404, and all four 404 on Snackday and Ballplayer. Draft rule: an article with `draft: true` is listed, served and in the sitemap only when `articleVisibilityFor(mode)` gives `with-drafts`, which is `SNACKDAY_RUNTIME_MODE=development` only; staging, production and the remote runtime (`runtime/web-surface.ts`, always `published-only`) leave it out and its URL is a 404. Each article page has a canonical link, a "Request a lesson" link to `/book`, and a plain link to its episode on the learn site (no embed, no media). `apps/web/test/coach-articles.test.ts` covers both modes.
- Coach JSON-LD: the coach home renders one `<script type="application/ld+json">` with a `SportsActivityLocation`, and each served article page renders one with an `Article` (author `Coach Ryan`, publisher the business). The values come from the typed `coachBusinessSchema` and `coachPersonSchema` in `app/coach/content.ts`; add no address, phone, price, rating, hours or geo until they are real facts. `app/coach/structured-data.ts` serializes with `JSON.stringify` and writes every `<` as `\u003c`, so a title cannot close the script element; `app/coach/json-ld.tsx` renders it on the server. A draft gets a block only where it is served, so never outside development. A data block does not execute, so `script-src 'self'` stays unchanged: `apps/web/test/coach-structured-data.test.ts` checks the policy and the escape, and `e2e/csp.test.ts` loads the home and an article on the `coach` brand (`coach.localhost`) in Chromium with no violation. `hasInlineScript` and `findThirdPartyRisks` (`apps/web/test/support/third-party.ts`) skip only a script whose sole attribute is `type="application/ld+json"` (exact lowercase, quoted); every other inline script, `application/json` included, is still flagged. The `https://dimasciobaseball.com/` and `https://schema.org` URLs in the block show up in `findThirdPartyRisks`, so coach page tests assert the exact URL set.
- The brand comes from the request `Host` header only; never read `X-Forwarded-Host` for it. `ballplayer.co`, `www.ballplayer.co`, and the dev host `ballplayer.localhost` (any port, any case) are Ballplayer; the coach hosts (below) are the coach brand; every other or missing host is Snackday.
- Tenant resolution: `apps/web/app/tenant/tenant.ts` turns a host into `{ organizationId, slug, modules, theme, primaryHost }` from an active `organization_hostnames` row of an active organization. `resolveTenant(db, host)` returns `undefined` for an unknown or pending host; `tenantForHost` serves that host as `FALLBACK_ORGANIZATION_ID` (Snackday) until the Worker entry answers it with 404. One bounded map per `Db` (`TenantCache`, at most 1,000 entries) keeps a hit 60 s and a miss 5 s; the fallback organization sits in the same map under a fixed key. `tenantResolver(db)` is built once per app in `lesto.app.ts` and `runtime/application.ts`. The brand router (`withBrandRoutes`, inside the kernel, so behind its rate limit and origin check) is the only caller of `resolve`; on a read error it logs `tenant.resolve_failed` with no host and uses the static map. The CSP wrapper (`withBrandSecurity`, outside the kernel in production) only calls `peek`, which never reads: it takes what the router last resolved for that host, or the static map for a request the router never saw (a kernel 403 or 429, a built asset). `brand.ts` is the shim: `brandForOrganization` maps `org_snackday`, `org_coach` and `org_ballplayer` to today's brands, and `brandForHost` reads `STATIC_HOST_ORGANIZATIONS`, which `apps/web/test/tenant-resolver.test.ts` keeps equal to the seeded active hostname rows.
- Change `organization_hostnames` rows only through migrations, and update `STATIC_HOST_ORGANIZATIONS` in the same change, until the Worker reads the table: the Worker CSP, a kernel refusal and an asset served before any page still use the static map.
- `apps/web/test/tenant-wiring.test.ts` proves the runtime and dev apps read the table (a database-only host and a pending host), that a refused request runs no hostname query, and that a failed read falls back. `apps/web/test/tenant-snapshots.test.ts` holds main's frozen answers (status, CSP, content type, cache control, a body marker) from base `29412b7`.
- `apps/web/app/server/brand-routing.ts` is the one wiring point. `routeBrands` only routes; it wraps the Lesto app in dev (`lesto.app.ts`) and production (`registerRuntimePages` in `runtime/web-surface.ts`). On the Ballplayer host, `GET /` renders `app/ballplayer/home-page.tsx` with no layouts and no client bundle, and `/fonts/*` serves `public/fonts`. Only the platform allowlist in that file (`/api/*`, `/__lesto/*`, `/styles.css`, `/client.js`) falls through to the shared app; every other Ballplayer-host request gets a plain 404 until Ballplayer has its own pages.
- Ballplayer styles live in `app/styles/app.css`, scoped by `data-brand="ballplayer"` on the page shell. Fonts are self-hosted under `public/fonts` with their OFL licenses. Load nothing from another origin and add no analytics to Ballplayer.
- Open Ballplayer locally: run `bun run --filter web dev`, then open `http://ballplayer.localhost:<port>/`.
- Every response from the app handler carries a strict Content-Security-Policy on every brand, from `apps/web/app/server/content-security-policy.ts`: `BALLPLAYER_CONTENT_SECURITY_POLICY` on the Ballplayer host, `COACH_CONTENT_SECURITY_POLICY` on the coach hosts, and `SNACKDAY_CONTENT_SECURITY_POLICY` on every other host. Every directive is `'self'` or `'none'`; the only other origin is `REEL_MEDIA_ORIGIN` (lesson posters), in Snackday's `img-src` only. Production applies it once, outermost, in `openRuntimeApplication` (`runtime/application.ts`), around the remote safety policy, release and asset wrappers; dev applies it with `secureBrands` in `lesto.app.ts`; the Cloudflare Worker (`worker.ts`) applies it with `withBrandSecurityFetch` around both the `ASSETS` binding and the app handler. Never rewrite the HTML body to satisfy the policy. Lesto's `[data-lesto-layout]` wrapper still carries an inline `style="display:contents"`; the policy blocks it and `app/styles/app.css` sets that display instead. It is the only inline style allowed until `@lesto/web` emits the wrapper without one. Island state stays in `type="application/json"` blocks, which the policy does not execute. Responses the `@lesto/runtime` transport writes itself (`/health`, `/readyz`, and its own 400, 413, 500 and 503 answers) and dev-server assets (`/styles.css`, `/@lesto-dev/*`) are outside the app handler and carry no policy.
- The policy protects minors on every brand. Do not loosen it (no new source or origin, `unsafe-*`, `data:`, `*`, hash, nonce, or removed directive) without Ryan's explicit yes. A page that needs a script or style gets it from a file on this origin.
- `lesto dev` appends inline live-reload and AI-overlay scripts and opens its HMR websocket on a second port, so the policy blocks them on every host in dev. `bun run e2e` serves the app handler without those dev tools and fails on any CSP violation except the blocked layout wrapper style, on every page it opens as every role. `e2e/csp.test.ts` also checks the exact policy header on both brands, the lesson poster from `REEL_MEDIA_ORIGIN`, and a 60-player roster that streams past React's first chunk.

## Repository layout

- `apps/web`: one Lesto origin for the marketing site and signed-in product.
  `apps/web/public/styles.css` is a committed symlink to `out/styles.css`: in `lesto dev`, Vite rewrites the page's `/styles.css` link to `/@lesto-dev/styles.css` and serves it from `public/`. Production does not read `public/`.
- `apps/ios`: native SwiftUI application and Xcode project (planned).
- `packages/domain`: framework-independent domain types, schemas, policies, and tests.
- `docs`: product, architecture, privacy, and decision records.
