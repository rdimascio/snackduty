- Studio → Lesto: `api/src/services/lesto-deploy.ts` shells out to the **external** `lesto` binary and zod-parses its `--json` verdict (`LestoDeployResult` in `@studio/shared`); comments state "lesto is NOT in this repo," with credential-scrubbed env and a prose fallback only for pre-`--json` lesto. Known ordering dragon: a verdict `schemaVersion` bump requires updating Studio first (fails loud otherwise).
- Snackday → Lesto: published `@lesto/*@^0.2.0` from npm (15 packages, `apps/web/package.json`) — no workspace links; the first genuine from-registry consumer. Snackday → Studio only as an _operand_ (`.studio-worktrees/`, `docs/studio-backlog.json` seeds board tasks).
- Studio → all repos as operand (worktrees, commits), which is orchestration, not a build dependency.

**Data/migration ownership** is cleanly partitioned: Studio owns its daemon SQLite (`api/src/db`, `migrate.test.ts`); Lesto owns the app migration _framework_ (`@lesto/migrate`, `@lesto/db`); Snackday owns its app schema and D1 config (`apps/web/lesto.db`, `wrangler.jsonc`; sprint task `L-e0745bce`); Roof holds only Keychain/session state (ADR 0008 intent already matches practice per `README.md`).

**Cross-repo atomic-change pressure: real but already absorbed by versioned seams.** I found no example of a change that _had_ to land atomically in two repos. The two live coupling points (deploy verdict, operator OpenAPI slice) each have an explicit versioning + drift-gate mechanism and a documented _ordering_ discipline instead. The pressure that remains is exactly what ADR 0007 targets: nothing declares which (Roof, Studio, Lesto, template) versions constitute a tested set.

**Coordination material is scattered and, critically, its newest layer is unprotected.** Product source of truth `docs/NORTH-STAR.md` lives in Lesto; execution truth is the Studio board; strategy docs (`STRATEGY_V2.md`, `DISTRIBUTION_PLAN.md`, `OPERATOR_CONVERSATION_DESIGN.md`) live in Studio; Roof's `FOUNDATION.md` is load-bearing design; and the platform ADRs 0001–0008 plus the Chief Architect packet sit **untracked** (`git status`: `?? docs/adr/`, `?? docs/platform/`) in Snackday — a repo with **no remote**. The platform's constitutional documents currently have the weakest durability of anything in the estate. The packet itself lists "No neutral coordination repository or signed platform manifest yet" as a known blocker; the filesystem agrees.

**Ownership/provenance is heterogeneous and matters for coordination-repo placement.** Remotes span a personal account (roof, studio), an org (lesto-run), and nothing (snackday). Studio physically lives under `~/every-io/` and its own license record flags an employment-IP provenance gate before publication; its name is explicitly provisional (naming deferred, `L-7455a0fb`). Roof, the _distributed_ customer binary, ships with no license/EULA text and no third-party notices file — a distribution-compliance gap independent of topology.

## 2. Evaluation of ADR 0005 and the packet

**ADR 0005** (independent repos + small neutral coordination repo; explicitly _not_ a shared implementation package or second board) is **directionally correct and its "evidence required" list is the right one** — this probe supplies the first item (inventory). Two material gaps:

1. **It never says who owns the coordination repo, where it lives, or its license/visibility.** Given the personal/org/employer-path split and Studio's unresolved title gate, ownership is the actual hard question the ADR was named for and currently dodges.
2. **It doesn't pick a canonicality rule for contracts.** "Compatibility manifests, schemas" is ambiguous between _canonical schemas move there_ (creates a new sync problem and risks runtime imports) and _hashes/pointers only_ (keeps product repos canonical). The existing, working pattern — Studio owns `openapi.json`, consumers vendor pinned slices with freshness gates — argues for hashes/pointers only.

**The packet** is high quality: D1–D7 are the right decision set, evidence-gated, with honest known-blockers. Specific notes: D1 recommendation matches my finding. D4's manifest is the single highest-leverage artifact (it converts today's implicit "ordering discipline" into a declared, testable compatibility set). D6's exact-SHA merge authorization is correctly listed as missing (`L-957b8149`). One inconsistency to fix: the packet's board section names ten task IDs (including `L-723fe37e`, `L-786014f7`, `L-5d3de617`, `L-9f36cd26`, `L-084f70a1`) but only five appeared in the board snapshot; reconcile before adjudication so "each ADR blocked only by its probe" is actually wired. One structural criticism: ADRs 0005–0008 are _platform-wide_ decisions recorded in the proof-app's repo; that's a bootstrapping convenience that should self-correct (see recommendation) — the packet should say so explicitly.

## 3. Options

**A. Product monorepo.** Atomic cross-repo edits; one gate. Against the evidence: four toolchains (SwiftPM/Xcode, Bun/TS ×2 with different bars, Xcode iOS), four release mechanisms (npm changesets; GH-Release+tap+R2 binaries; notarized .app+appcast; wrangler app deploys), and four license postures (MIT public, Apache private-pending-provenance, unlicensed proprietary, UNLICENSED). A monorepo entangles Lesto's public MIT surface with Studio's clouded-title Apache code and Roof's proprietary client — the provenance gate would then block _everything_. It also erases the "Snackday consumes Lesto from real npm" proof, the platform's own dogfood signal. No observed atomic-change need justifies paying this.

**B. Independent repos + small neutral coordination repo (ADR 0005 as proposed).** Matches release authority, license boundaries, and the already-working versioned seams. Cost: one more repo to keep honest; staleness risk if the manifest isn't generated/verified mechanically.

**C. Status quo (distributed docs).** Zero new structure, but it is _currently failing_: the platform ADRs are untracked in a remote-less repo; north-star, strategy, and contract truth live in three different products, each of which would gain improper authority over the others if anointed (ADR 0005's own analysis, which I confirm).

## 4. Recommendation

**Accept ADR 0005 (Option B) with three amendments; adopt the packet's D1 accordingly.**

1. **Ownership amendment.** The coordination repo is created under a clean, non-employer, non-personal org (lesto-run or a new platform org — human choice below), private initially, plain-docs license (CC-BY or Apache-2.0-docs), with the repo's _merge authority = the Chief Architect decision process_, not any product team. It must not be created under `every-io` or blocked on Studio's title gate — the manifest must be able to name Studio artifacts without inheriting Studio's provenance risk.
2. **Canonicality amendment.** The coordination repo stores **accepted cross-product ADRs, the signed release manifest (versions + content hashes + supported ranges + migration/rollback coordinates), runbooks, demo definitions, and evidence indexes — never canonical schemas or code**. Each product repo remains canonical for its own seam (Studio: `api/openapi.json` and `/v1`+WS; Lesto: deploy-verdict schema and package semver; template contract: Lesto scaffold). Consumers keep the proven vendored-slice + freshness-gate pattern (`regen.py` model). This makes ADR 0005's "no product build imports the coordination repository at runtime" true by construction.
3. **Migration amendment.** On acceptance: commit Snackday's `docs/adr/` + `docs/platform/` immediately (they are one `rm -rf` from nonexistence), give Snackday a private remote, then _move_ ADRs 0005–0008 and the packet to the coordination repo at its creation, leaving 0001–0004 in Snackday (they are Snackday's own integration contract) with pointers.

Interim step (independent of topology): Snackday needs a remote this week regardless.

## 5. Risks

- **The coordination repo rots** into a stale mirror if the manifest is hand-written. Mitigation: manifest generation must be a script that _derives_ versions/hashes from pinned commits (the `L-40f386e3` probe), re-runnable and byte-reproducible, with a non-blocking verify check in each product CI initially.
- **Scope creep** into a shared package or second board — explicitly forbidden by ADR 0005; enforce with the acceptance greps below.
- **Signing authority is undefined** while `L-957b8149` (SHA-bound merge authorization) is unbuilt and Studio automation is release-blocked; a "signed manifest" signed by an unaccountable key is theater. Sequence: manifest format + generation first, signature authority after D6 lands.
- **Roof's missing license** becomes a launch incident the first time the notarized app ships to an outsider (no EULA, no third-party notices despite a distribution pipeline that already exists).
- **Unpushed work** (Roof ahead 12, Studio ahead 2, Snackday remote-less) means the manifest's "current commits" are one disk failure from unreproducible.

## 6. Falsification / reversal triggers

- **Monorepo trigger (makes ADR 0005's trigger measurable):** if, over any rolling month after the manifest exists, ≥3 changes require same-day paired landings across ≥2 product repos _despite_ the versioned seams (measured by manifest entries whose components must move together, or reverts caused by cross-repo ordering), re-open D1 toward a monorepo or repo-merge of the tightly coupled pair.
- **Fold-back trigger:** if the coordination repo acquires runtime-imported code, a package manifest with dependents, or duplicate task tracking, stop and fold its contents back into product repos — Option C beats a corrupted Option B.
- **Contract-drift trigger:** a Roof runtime decode failure or Studio verdict-parse failure against a manifest-declared-compatible set falsifies the "hashes/pointers only" amendment — canonical schemas may then need to move to the coordination repo with generated clients.
- **Ownership trigger:** if Studio's provenance review finds transplanted employer code, the manifest must be able to exclude/replace the Studio artifact without restructuring — if it can't, the coordination design failed its purpose.

## 7. Decisions requiring a human

1. **Org and name** for the coordination repo (interacts with `L-7455a0fb`: "Studio" is provisional — do not bake it into a public platform repo name), and its visibility/license.
2. **Roof licensing posture** (proprietary EULA vs source-available vs open) and third-party notices — blocking for any external distribution.
3. **Manifest signing authority** (which key, held by whom) — after D6.
4. **Studio provenance Gate-1 sign-off** (employment-IP review) — already human-gated in `license-decision.md`.
5. **Packet adjudication itself** (D1–D7 accept/amend/reject) — this report is input to `L-710ba74e`/`L-76601e17`, not a substitute for the deciding actor's record.

## 8. Acceptance tests

1. **Inventory (this probe, `L-9d682737`):** the coordination repo's first commit contains this inventory; every claim carries a file reference; a re-run of the probe reproduces the dependency-direction table.
2. **Manifest prototype (`L-40f386e3`):** a script emits `{roof: VERSION+commit, studio: version+sha256(api/openapi.json)+commit, lesto: package versions+dist digests, snackday: commit+declared @lesto range, deploy-verdict schemaVersion}` for the current four repos; running it twice from the same pins is byte-identical; verification recomputes every hash from the pinned commits and fails on any mismatch.
3. **No-runtime-import gate:** CI grep in each product repo proving no dependency on the coordination repo (no package/submodule/path reference); conversely, grep in the coordination repo proving no `package.json` dependents, no source directories beyond manifest tooling.
4. **Roof↔Studio compatibility:** `Scripts/check-fixture-freshness.sh` passes against the exact Studio commit named in the manifest; `OperatorServerContractTests` green; an intentionally majored fixture makes the compat gate fail loud.
5. **Studio↔Lesto compatibility:** `lesto-deploy.test.ts` fixtures cover the manifest's declared verdict `schemaVersion`; an unknown _newer_ schemaVersion yields a typed loud failure, never the prose fallback.
6. **Lesto↔Snackday compatibility:** Snackday `bun run gate` green after a clean from-registry install of the manifest's `@lesto` range (reuse the `scaffold-real-install.yml` pattern — the linked-workspace trap is a known false-green).
7. **ADR durability:** ADRs 0001–0008 committed and pushed; 0005–0008 relocated to the coordination repo with back-pointers; `git log` in Snackday shows no platform-ADR edits after the move.
